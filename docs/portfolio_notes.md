## 1. 30秒で説明する

> 市販サービスやパッケージを導入するとき、「うちの会社で使えるか」を、製品資料・営業説明と自社の業務ルールを照合して判断する作業があります。
> ReadyProof AI は、この照合をAIが根拠付きで下書きし、ベンダーへの質問、受入テスト仕様書、導入判断までを一つの流れで支援するWebアプリです。
> AIの出力は必ず「下書き」として扱い、確定は人が行います。「資料に書いていない」ことを「対応不可」と判断しないなど、導入判断で起きやすい誤りを、プログラムの安全装置で防いでいます。

公開デモ：https://yukon2051-readyproof-ai.hf.space（架空データ・料金なし）

---

## 2. 解決したい業務課題（自分の経験から）

- 導入検討では、営業説明の「できます」と、自社の細かいルール（金額の境目、例外、権限）が合っているかの確認が抜けやすい
- 資料に書いていないことを「できない」または「できるだろう」と思い込みやすい
- 確認した結果が、質問・テスト・導入判断にばらばらに残り、根拠をたどれない

ReadyProof AI では、これを「入力2つ（製品の資料・自社のルール）→ 出力2つ（診断結果・受入テスト）→ 人の導入判断」の5段階にまとめた。

## 3. 自分が行ったことと、AIが行ったことの区別

| 区分 | 内容 |
|---|---|
| **自分（利用者）** | 業務課題の設定と要件定義（最初の仕様書）。画面の流れ（入力2つ → 出力2つ → 判断）の決定。デモの方針（見るだけ・本物のAI出力・完了した案件の見本）の決定。費用上限（月6,000円）と公開先（Hugging Face の有料プラン契約）の決定。画面の言葉・配置・色の細かい指示とレビュー。Excel を「仕様書 兼 成績書」にする判断。残件（BL-001・BL-002）の優先順位付け |
| **AI（Claude Code）** | プログラムの実装、自動テスト（122件）、設計書・README などの文書の下書き、公開用スクリプト、画面の動作確認 |
| **一緒に行ったこと** | 不具合の原因調査と対応方針の決定（例：接続が切れたときの自動復元）、AIの出力品質の確認（実際の Claude API での試行） |

面接では「コードを書いたのはAI。自分の役割は、要件を決め、出来上がったものを業務の目で確かめて直させたこと」と正直に伝える。

## 4. 主な設計判断と理由（よく聞かれそうな順）

### 4-1. AIの「思い込み」を防ぐ安全装置
- **判断**：AIの診断は必ず検証し、条件を満たさないときは自動で「確認が必要」に下げる
- **理由**：導入判断で一番困るのは「できないのに、できる」と判断すること
- **仕組み**：引用が資料に実在するかを確認する／根拠がない「見込み」は情報不足に下げる／「対応不可」は資料の記載か確認済みの発言がないと付けられない（記載がない＝対応不可にしない）

### 4-2. 「残る条件」を2種類に分けた（BL-002）
- **きっかけ**：実際の Claude API で試すと、「10,000円ちょうどの扱い」のようにテストで確かめればよい点まで未確認の条件に入り、安全装置で「情報不足」に下がった（8件中3件が期待より慎重な判定）
- **判断**：条件を「ベンダー確認が必要」と「実機テストで確認すること」に分け、後者は見込みを保ったうえで必ずテストにする
- **ポイント**：安全装置をゆるめたのではなく、確認の手段（質問かテストか）を分けた

### 4-3. 自社ルールの入力をAIが聞き取る（BL-001）
- **課題**：社内規程が文章になっていない、どの観点を確認すべきか分からない利用者には入力が重い
- **判断**：AIが製品資料を踏まえて「自社について聞くべき質問」を作り、1問ずつ答えてもらう。「分からない・未定」は推測で埋めない
- **確認**：実際の Claude API で、資料の位置（例：スライド2の金額別承認ルート）を根拠にした質問が出ること、不自然な回答（年数に 10000）を勝手に直さず再確認事項にすることを確かめた

### 4-4. デモは「見るだけ」、出力は本物のAI
- **判断**：デモの入力は固定、出力は本物のAIに事前に作らせた結果を表示。決定ボタンはすべて押せない
- **理由**：手で作った見本を「AIの出力」として見せるのは誤解を招く。採用担当者に料金をかけずに、本物の結果を見てもらうため
- **工夫**：AIに送った入力の指紋（SHA-256）を保存し、入力が変わったら古い出力を表示しない

### 4-5. 公開しても費用が膨らまない仕組み
- 自分の案件でAIを使うにはAIパスワードが必要
- 実行前に費用の見込みを表示し、「予約 → 実行 → 実績で確定」の順で記録（同時に押されても上限を超えにくい）
- 利用記録は非公開の保存場所に置く（公開サイトが再起動しても月の上限が効く）。記録できないときはAIを実行しない

### 4-6. 公開先の変更
- 最初は Streamlit Community Cloud（無料）で公開したが、画面の部品が断続的に読み込めず表示されない問題が解決しなかった
- 原因の切り分け（版の固定、再構築）を試したうえで、Hugging Face Spaces（月9ドル）に移した。判断材料は「採用担当者が開いたときに確実に表示されること」

## 6. 課題・まだできていないこと（正直に言う）

- AIの診断精度は少数の試行でしか確かめていない（正解データを作って継続的に評価する必要がある）
- 利用者の認証がない（名前は自己申告。正式な承認には使えない）
- 利用記録の保存は1台で動かす前提の作り（利用者が増えたらデータベースが必要）
- 画像だけのPDF（OCR）、図・画像の意味は読み取らない
- 公開サイトの書き込み用トークンは、権限を絞ったものへの差し替えを手順化した段階（`docs/deploy.md`）

## 7. 想定質問と答えの例

**Q. AIが間違えたらどうするのですか？**
A. AIの出力はすべて下書きで、確定は人が行います。そのうえで、引用が資料に実在するかをプログラムで確かめ、根拠のない「見込み」や「対応不可」は自動で「確認が必要」に下げます。間違いをゼロにするのではなく、間違いが判断に混ざらない流れにしました。

**Q. 自分で作ったのですか？**
A. コードは Claude Code（AI）が書きました。私は、要件定義、画面の流れの設計、デモや費用の方針を決め、出来上がったものを業務の目で確かめて修正させました。例えば、AIが「テストで確かめればよいこと」まで未確認扱いにする問題を実際のAIで見つけ、条件を2種類に分ける改善につなげました。

**Q. 一番苦労したことは？**
A. 「AIの出力をそのまま信じない」ことと「使いやすさ」の両立です。安全装置を強くすると、慎重すぎて使えない判定が増えました。そこで安全装置はゆるめずに、条件を「質問で確かめるもの」と「テストで確かめるもの」に分けることで解決しました。

**Q. 実務ではどう使えますか？**
A. 製品選定の段階で、営業説明の「できます」を根拠付きで整理し、ベンダーへの質問書と受入テスト仕様書を同じ根拠から作れます。テスト結果を記録すれば、Excel が成績書になり、導入判断の理由も残ります。

## 8. 職種ごとの伝え方

- **社内SE**：導入時の要件確認・受入テスト・判断記録を、根拠をたどれる形で回す仕組みを作った
- **DX推進**：生成AIを「下書き＋人の確定＋プログラムの安全装置」で業務に入れる設計を、実際に動く形で示した
- **ITコンサルタント**：営業説明と自社要件のギャップを、確認方法（質問・テスト）まで分けて整理する方法論をツール化した
- **プリセールス**：顧客がどこで迷うか（「書いていない＝できない？」）を理解し、質問とテストで確かめる流れを作った
