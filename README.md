# ReadyProof AI（AI受入テスト・導入確認支援システム）

> 「うちの会社で使える？」に答えるAI

**公開デモ：https://yukon2051-readyproof-ai.hf.space** （架空データの3件のデモ・料金なし。自分の案件でAIを使うにはAIパスワードが必要です）

ベンダーの製品資料や営業説明の録画と、自社の業務ルール・作業手順を照合し、そのまま使える見込み、設定が必要な部分、追加対応が必要な部分、確認が必要な点を根拠付きで整理します。さらに、ベンダーへの質問、改修・設定変更依頼書、受入テストの作成と結果管理まで支援します。

## 解決する業務課題

SaaS やパッケージの導入検討では、次のことがよく起こります。
- 提案書の「対応可能」や営業の口頭説明を、そのまま「自社で使える」と受け取ってしまう
- 上位プラン限定・オプション・将来予定などの条件が、比較表や議事録から抜け落ちる
- 導入後の受入テストで、どの要件をどの根拠で確認したのかが追えない

ReadyProof AI は、**「資料や営業説明から分かる見込み」と「実機で確認できたこと」を分けて**管理し、根拠（資料のページ・スライド、発言の時刻と話者）を最後まで追えるようにします。

- 対象：社内SE、情報システム部門の導入担当者、ITコンサルタント、利用部門の担当者
- 既存作品との違い：AI-BIC（業務課題と改善案の整理）、ChangeScope AI（変更による組織・システムへの影響整理）とは異なり、本作品は「候補製品が自社業務に合うか」「不足をどう埋めるか」「実際に要件を満たしたか」に集中しています（連携は第1版では対象外）

## 3件のデモ（架空データ・料金なし・各3分程度）

| デモ | 主題 | 見どころ |
|---|---|---|
| 1 経費精算サービス | PowerPoint 資料と社内規程を照合 | スライドの表から引用／金額別承認は「設定で対応見込み」／自己承認の禁止は記載なし→質問→回答で更新／ノートは初期状態で対象外／9,999円・10,000円の境界値テスト→設定漏れで不合格→設定変更依頼→再テスト合格 |
| 2 生産・在庫管理システム | 現場の作業とパッケージ仕様の差 | 「ロット管理 ○」だけで適合としない／複数原材料ロットは有償オプションが条件／オフライン入力は記載不足→回答で「対応不可の記載あり」／運用・追加開発の候補比較／改修依頼（費用は未回答のまま）／一部合格でも要件全体は未確認 |
| 3 社内アカウント管理 | 営業発言と資料の照合 | 自社の質問を営業の確約と誤認しない／「上位プランで対応」を標準プランの機能にしない／資料と営業説明の矛盾／「確認して回答」は未回答、「予定」は将来予定／時刻と引用付きの書面確認の質問 |

デモは「見るだけ」です。入力（資料・録画・自社のルール）は固定で、変更できません。出力（診断結果・受入テスト仕様）は、この固定の入力を本物の AI（Claude、claude-opus-5-5）に事前に渡して作った結果をそのまま保存し（`readyproof/demos/ai_results/`、作成：`scripts/make_demo_ai.py`、2026-11-04 実測：保存した出力の作成費 約114円、やり直し分を含む実費 約160円）、画面ではそれを表示するだけです（表示時に有料APIは呼びません）。AIに送った入力の指紋（SHA-256）も保存し、入力が変わった場合は古い出力を表示せず、作り直しを求めます。デモでは、確認・確定・保存・記録・導入判断などの決定ボタンはすべて非活性で、押せません（自分の案件でだけ使えます）。デモは「完了した案件の見本」です。AIの出力のあとに人が行う作業（ベンダーへの質問と回答、回答を踏まえた診断の見直し、「要確認」が残るテストの修正・確定、実機テストの結果（不合格→再テストを含む）、対応方法の採否、導入判断）は、架空の担当者の記録として `readyproof/demos/followup.py` に定義しています（名前に「（架空）」を付けて表示）。AIの最初の診断は「以前の診断」として残ります。業務ルールの自動テストには、手で作った筋書き版（`build_scenario`：質問・回答・不合格→再テストなど）を使い、期待結果と確認ポイントを `EXPECTED` で検証しています。

## 画面の構成（入力2つ → 出力2つ）

| 段階 | 画面 | 利用者がすること | できるもの |
|---|---|---|---|
| 入力1 | ① 製品の資料 | 提案書・機能一覧・マニュアル（PDF/Word/Excel/PowerPoint/テキスト）、営業説明の録画（MP4/WebM/MOV）や字幕（VTT/SRT）を1つの欄に入れる | 位置（ページ・スライド・表の行・発言時刻）付きの読込結果。スライド別の対象選択、話者・発言の確認 |
| 入力2 | ② 自社のルール | 質問に答える。聞き方は2つ：AIが製品の資料を踏まえて質問を作る（料金あり）／決まった質問（① 業務の種類 ② 必ず守るルール ③ 例外・未定 ④ 誰が使うか・権限 ⑤ 使うときの条件・料金なし）。規程ファイルや手入力も可 | 自社の要件（版・確定状態つき）。分からない点は推測せず「未確定」 |
| 出力1 | ③ 診断結果 | 判定と根拠を確認し、不明点は質問、合わない部分は対応方法・依頼書へ | 要件ごとの「そのまま使えるか」の判定（6区分）と根拠（元資料の前後＋引用に印）、質問書・依頼書（Excel） |
| 出力2 | ④ 受入テスト | テストを確定し、実機で試した結果を記録 | 受入テスト仕様書 兼 成績書（Excel）。テスト仕様は AI が下書きし、人が確認・確定。残った問題と人の導入判断 |

受入テスト仕様書 兼 成績書（Excel）は「表紙（テスト結果のまとめ・実施期間、作成者・確認者・承認者の記入欄）／概要（目的・対象範囲・対象外・テスト環境・合否判定基準・不合格時の扱い）／テスト項目（事前条件・テストデータ・番号付き手順・期待結果・合否判定基準・根拠・最新の結果）／要件との対応表（足りない観点の表示）／実施記録（再テストを含む全履歴）」の5シートです。アプリの画面で記録したテスト結果が自動で入るため、テスト成績書として保存できます。アプリを使わずに記録する場合は、まだ結果のない行の黄色の欄に記入します。

| 判断 | ⑤ 導入判断 | 残った問題と根拠を確認し、導入するかを判断する | 判断（判断者・日付・理由・条件）と導入確認レポート（Excel） |

デモでは、① 製品の資料 → ② 自社のルール → ③ 診断結果 → ④ 受入テストの順に、約3分（4ステップ：入力1 → 入力2 → 出力1 → 出力2）で案内します。

## 対応形式と読める範囲（制限）

- PowerPoint：タイトル・テキストボックス・表（行単位）・グループ内の図形・発表者ノート（初期状態で対象外）。**画像内の文字、矢印・図形の位置関係、グラフ、SmartArt、アニメーションは理解しません**（警告を表示）。同じスライドに「金額」と「承認者」があるだけで金額別承認と判断しません
- PDF：文字情報を含むもののみ（OCR なし）。表は列が崩れることがあります
- Word：本文・見出し・表。ヘッダー/フッター・テキストボックス・コメントは対象外
- Excel：保存済みの値を読みます（数式は計算しません）。非表示シートは初期状態で対象外
- 旧形式（.doc / .xls / .ppt）は新形式または PDF への変換を案内します
- 録画：音声の発言内容のみ（映像・画面共有の内容は対象外）。**話者の自動判定はありません**。動画本体は JSON に保存されません

## 話者と発言の確認方法

1. 「① 製品の資料」→ 読み込んだ録画の「詳しく確認する」→「話者をまとめて設定する」で、自動ラベル（例：話者1）ごとに役割（営業担当者・自社担当者など）と氏名を設定し「確認済み」にする
2. 発言ごとに文章を修正（原文は残り、履歴が付く）し、種類（質問・回答（条件付き）・将来予定・未回答・調査中 など）を選び、内容確認を「確認済み」にする
3. 数値・金額・否定表現・製品名に注意フラグが付きます。聞き取れない箇所は創作せず「聞き取り不能」とします
4. 確認済みのベンダー発言だけが「確定した営業回答」として扱われます。未確認の発言は根拠に使えますが、警告が付きます

## 根拠検証の限界

プログラムが確認するのは「引用がその資料・発言に実在するか」「その箇所が分析対象か」「対象製品の資料・録画か」「確認済みか」までです。**引用が要件を満たす意味かどうか（妥当性）は人が確認します。** 検索で見つからないことは、機能がないことを意味しません。

## 起動方法（Windows）

```powershell
# 初回のみ：Python 3.12 の仮想環境を作り、ライブラリを入れる
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt

# 起動（ブラウザが開きます）
.venv\Scripts\streamlit run app.py
```

- API キーがなくても、デモ・手動入力・AIを使わない検索・Excel/JSON 出力・ローカル文字起こしが使えます
- ローカル文字起こしは `requirements-local.txt`（`requirements-dev.txt` に含む）で入ります。初回にモデル（small・約480MB）を自動ダウンロードします。公開サイトには入れていません（重いため。録画は会議ツールの文字起こし読込で使います）
- **ブラウザを再読込すると未保存の作業は消えます。** サイドバーの「作業を保存（JSON）」で保存し、「保存した作業を開く」で再開してください

## 設定（AI を使う場合・費用）

`.streamlit/secrets.toml`（Git に入れない）または環境変数で設定します。

```toml
ANTHROPIC_API_KEY = "（自分のキー）"
RP_ACCESS_CODES = "code-a,code-b"          # 利用コード（共有すると回数枠も共有）
RP_USAGE_STORE_PERSISTENT = "true"         # 利用記録の保存先が永続的な場合のみ true
RP_USAGE_LEDGER_PATH = "data/usage_ledger.jsonl"
```

- 初期値：月のアプリ予算 6,000円、AI生成は1コードにつき月3回（再生成も1回）、診断は1回最大10要件、テスト生成は最大15件、依頼書は1件。上限はすべて `RP_` で始まる環境変数で変更できます（一覧は「設定・利用枠」画面）
- 実行前に送信先・送信内容・費用見込み（出力上限まで使い再試行1回を含む最大額）を表示します
- 永続的な利用記録の保存先がない環境では、有料処理を停止します
- アプリ予算は請求額の保証ではありません。Anthropic コンソール側の支出上限も設定してください
- モデルは `claude-opus-5-5`（設定 `RP_MODEL` で変更可）。料金単価も設定値です（公式価格表で確認してください）

## データの取り扱い

- 公開環境では、外部送信が許可された資料・録画、または匿名化した情報だけを使ってください。録画は参加者の利用許可を確認してから登録してください
- アップロード（アプリ内）／音声処理（サーバー内・外部送信なし）／文字の AI 送信（Claude API）は別の操作で、AI 送信の前に送信先と内容を表示します
- 資料・発言の中の命令はアプリへの指示として扱いません。マクロ・埋め込み・外部リンクは実行しません
- 認証はありません。記録上の操作者は「利用者」と表示され、本人確認や正式な承認ではありません
- サンプルの会社・製品・人物・資料・録画はすべて架空です
